One process, three boundaries worth tracking: the radio link (shared, slow, serialized), the per-player queue inside the bot (keeps one slow player from blocking another), and the HTTP hop out to the external game service, which is where the actual Zork interpreter lives.

Why a queue per player

ZorkBot._enqueue() gives each pubkey_prefix its own bounded asyncio.Queue and worker task. A slow game turn for one player never delays another's — they're isolated queues, not a shared one.

Why one send lock

Radio bandwidth is the real bottleneck. runner.py routes every outbound packet — channel replies, DMs, watcher fan-out, adverts — through a single asyncio.Lock spaced by send_spacing_seconds, so the mesh never sees a burst.

Where the game actually runs

Zorkbot holds no Zork state. game_client.py is a thin HTTP client; the interpreter, session pool, and save files live in a separate zorkd process reached at GAME_URL.
